# Fabel — план работ

Цель проекта, принятые решения, архитектура и статус этапов.
План обновляется по мере разработки.

---

## 1. Что строим

Платформа для обучения программированию. Владелец приглашает друзей, выдаёт им
логин и пароль, они изучают материалы и решают задачи, прогресс сохраняется.

Ключевое отличие от литкода: не только «напиши функцию», но и обучение —
сначала теория (видео и статьи), потом задачи по пройденному.

---

## 2. Принятые решения

Ниже описаны требования и принятые решения.
При расхождениях с первоначальным ТЗ используем эти требования.

### 2.1. Авторизация — по выданным кредам

> «Логин будет происходить по тем кредам, которые я выдам пользователю.»

Регистрации на сайте нет. Учётные записи заводит владелец, он же передаёт
логин и пароль ученику.

Это **отменяет** пункт первоначального ТЗ про провайдеров GitHub + Google:
в ТЗ было противоречие (во вступлении — логин/пароль от владельца, в разделе
стека — OAuth-провайдеры), оно разрешено в пользу выданных кредов.
Проверка №9 из ТЗ («войти через GitHub») читается как «войти под выданными
кредами».

Auth.js (NextAuth v5) остаётся — используется его Credentials-провайдер.

### 2.2. Темы — пять штук, не dark/light

> «Верни темы которые были ранее.»

Селект в шапке с пятью темами вместо переключателя «тёмная/светлая»:

- тёмные: **Графит** (по умолчанию), **Уголь**, **Контраст**;
- светлые: **Туман**, **Пергамент**.

Цвета спокойные, графитовые — на платформе проводят много времени, глаза не
должны уставать. Вариант «Контраст» — для тех, кому нужна бодрость.
Темы задаются полными наборами CSS-переменных, `prefers-color-scheme` не
используется: выбор пользователя — единственный источник истины.

### 2.3. Запуск кода отделён от проверки

> «"Запустить" будет показывать результат без отправки в тесты, а кнопка
> отправить на проверку — уже будет проводить тесты и помечать задачу
> как пройденную или не пройденную.»

Две кнопки:

| Кнопка | Что делает |
|---|---|
| **Запустить** | Выполняет код, показывает вывод и ошибки. Тесты не запускаются, зачёта нет. Черновик для отладки. |
| **Отправить на проверку** | Прогоняет тесты, показывает «Пройдено N из M», при всех зелёных отмечает задачу решённой. |

### 2.4. Обучающие материалы и порядок прохождения

> «Сначала я смотрю видео и читаю статью на первой страничке темы, по нажатию
> кнопки перехожу на вторую страничку, первая помечается как прочитанная и так
> далее. Как только вся информация закончена по теме, идут задачи.
> Все это объеденяется в какой-то блок.»

Блок = **модуль**. Внутри модуля строгий порядок: сначала все уроки, затем
задачи. У уроков свой прогресс — «прочитано», наравне с «решено» у задач.

Урок собирается из блоков:

- `text` — теория в мини-markdown;
- `video` — ссылка на видео, **проигрывается прямо на сайте**;
- `article` — ссылка на внешнюю статью.

Владелец должен уметь добавлять такие материалы сам, правкой файлов в репозитории.

## 3. Стек

Согласован, менять без веской причины нельзя.

| Слой | Выбор |
|---|---|
| Каркас | Next.js 16, App Router, TypeScript, код в `src/`, алиас `@/*` |
| Стили | Tailwind v4 |
| Редактор кода | CodeMirror 6 |
| Запуск JS | Web Worker в браузере, без библиотек, с таймаутом |
| Авторизация | Auth.js (NextAuth v5), Credentials-провайдер |
| БД | Vercel Postgres (Neon) + Drizzle ORM |
| Хостинг | Vercel |

Задачи и учебные материалы хранятся **файлами в репозитории** и версионируются
в git. В БД только пользователи и прогресс.

Next.js 16 заметно отличается от прежних версий: Turbopack по умолчанию,
`params` и `searchParams` — промисы, `middleware` переименован в `proxy`,
команда `next lint` удалена. Перед правками сверяться с документацией
в `node_modules/next/dist/docs/`.

## 4. Архитектура

### 4.1. Запуск кода

`src/lib/runner` — шов между интерфейсом и исполнителем. Страница задачи знает
только `Task`, `Runner` и `RunResult`; выбор исполнителя идёт по `task.kind`
в `index.ts`. Благодаря этому добавление Go через серверный раннер или
DOM-задач через iframe не потребует правок страницы.

Скрипт воркера собирается строго в таком порядке:

```
строка 1        пролог: подмена console.*
строки 2..N+1   код пользователя — как есть, без обёрток
дальше          харнесс: сравнение, прогон тестов, отправка результата
```

Код не оборачивается в `new Function` намеренно: так номера строк в `error.stack`
совпадают с номерами в редакторе с точностью до известного смещения
(`LINE_OFFSET = 1`, пролог занимает ровно одну строку). Функции харнесса
объявлены через `function`, поэтому поднимаются в начало скрипта и доступны
прологу во время выполнения кода ученика.

Требования к харнессу: глубокое сравнение результатов, отдельный `try/catch`
на каждый тест (падение одного не останавливает остальные), `solution`
вызывается ровно один раз на тест, логи и результаты тестов — разные поля.

### 4.2. Контент

- `src/lib/tasks/` — задачи, по файлу на задачу.
- `src/lib/content/modules/` — модули с уроками.
- `src/lib/content/index.ts` — сборка маршрута модуля: уроки, затем задачи.

### 4.3. Прогресс

`src/lib/progress.ts` — единственное место, знающее, где лежит прогресс.
Сейчас localStorage; на этапе 2 меняется на БД, компоненты не трогаются.

## 5. Этапы

### Этап 1 — MVP страницы задачи ✅ сделано и проверено

- Каркас Next.js + Tailwind v4 + CodeMirror 6.
- Раннер: типы, выбор по `kind`, `browserJsRunner`, харнесс воркера.
- Пять задач типа `algorithm`.
- Страница задачи: описание, редактор, консоль, обе кнопки.
- Пять тем, селект в шапке.
- Модули с уроками (видео, статьи, текст) и прогрессом.
- Прогресс в localStorage.

Проверки из ТЗ — все пройдены:

| # | Проверка | Статус |
|---|---|---|
| 1 | Корректное решение → все тесты зелёные | ✅ |
| 2 | Рантайм-ошибка → сообщение и корректный номер строки | ✅ строка и символ точные |
| 3 | Бесконечный цикл → воркер убит по таймауту, UI жив | ✅ 4 с |
| 4 | Падение одного теста из нескольких | ✅ 3 успеха + 1 провал |
| 5 | Массив/объект в `expected` → глубокое сравнение | ✅ |
| 6 | Код без `solution` → понятное сообщение | ✅ |
| 7 | `console.log` не задваивается | ✅ |

### Этап 2 — авторизация и сохранение прогресса ⬅ следующий

**Вход только по выданным кредам.**

1. **Схема БД** (`src/lib/db/schema.ts`, Drizzle):
   - `users` — `id`, `email` (он же логин), `name`, `passwordHash`, `role`
     (`student` / `teacher`, пригодится на этапе 4), `createdAt`;
   - `submissions` — `userId`, `taskSlug`, `code`, `passed`, `createdAt`;
     «решено» = существует запись с `passed = true`;
   - `lessonProgress` — `userId`, `lessonId`, `readAt`; таблица добавлена
     сверх первоначального ТЗ, потому что появились уроки со своим прогрессом.
2. **Клиент БД** — Neon через `DATABASE_URL`.
3. **Auth.js v5**: `src/lib/auth.ts`, Credentials-провайдер, стратегия сессий
   `jwt` (обязательна для Credentials), пароли под хешем (scrypt из `node:crypto`,
   без лишних зависимостей), защита от подбора — сравнение в постоянное время.
4. **Заведение учёток владельцем** — скрипт `npm run user:add`, который создаёт
   пользователя с логином и паролем. Регистрации в интерфейсе нет.
5. **Страница входа** `/login`, редирект неавторизованных.
6. **API**: `src/app/api/submissions/route.ts` — сохранение решения;
   endpoint для отметки урока прочитанным.
7. **Перевод прогресса на сервер**: `src/lib/progress.ts` начинает ходить в API;
   отметки «решено» и «прочитано» показываются вошедшему пользователю.

Проверка: войти под выданными кредами → решить задачу → отметка «решено»
появилась; выйти и войти снова → отметка на месте.

**Что нужно от владельца:** строка подключения `DATABASE_URL` от Neon/Vercel
Postgres. Аккаунты и ключи заводит владелец лично.
Локально этап проверяется на встраиваемом Postgres, так как Docker и psql
в системе не установлены.

### Этап 3 — деплой на Vercel

Подключить репозиторий, задать переменные окружения (`DATABASE_URL`,
`AUTH_SECRET`), прогнать миграции, проверить вход и сохранение на боевой БД.

**Что нужно от владельца:** аккаунт Vercel, репозиторий на GitHub, доступ к БД.

### Этап 1b — задачи типа `dom` (после обязательных)

«Оживи HTML»: автор даёт разметку, ученик пишет только JS. Исполнение
в `<iframe sandbox="allow-scripts allow-downloads">` **без** `allow-same-origin`,
чтобы у кода был opaque origin и он не дотянулся до основной страницы и cookies.
Типы `DomTask` и `DomCheck` уже описаны в `runner/types.ts`.

### Этап 1c — задачи типа `tests`

Инверсия `algorithm`: платформа даёт реализацию, ученик пишет тесты. Качество
оценивается прогоном против эталонной реализации (всё должно проходить) и против
набора «мутантов» — каждого мутанта должен поймать хотя бы один тест ученика.

### Этап 4 — трекер задач, Jira-подобный

Эпик → стори → задача. Эпики и стори создаёт владелец (роль «преподаватель»),
задачи — ученики. Поля: название, описание, исполнитель, статус, оценка времени,
факт. Статусы `todo → in progress → done` (возможно `review`), канбан-доска
с перетаскиванием. Требует ролей пользователей, поэтому зависит от этапа 2.

## 6. Правила работы

- Не начинать следующий этап, пока предыдущий не работает end-to-end.
- Обязательные этапы: 1, 2, 3. Остальные — после, отдельно.
- Дизайн под десктоп и ноутбук: на телефоне код почти никто не пишет.
- Интерфейс и материалы на русском.
